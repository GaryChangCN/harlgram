# AI-native 协作工作流

AI-native 的落点是可接力的源码、可复现的命令和可追溯的结果。项目不依赖某个 agent 的会话记忆，也不自动处理真实聊天内容。

## 每个任务的输入与输出

开始前读 `../AGENTS.md` 和 `STATUS.md`，确认用户当前要求、已有授权、设备选择、正在并行修改的文件和尚未解决的问题。只把与当前行为相关的上游源码和文档读入上下文。

为本次修改建立一个小闭环：用户会如何触发、当前行为是什么、期望结果是什么、失败时如何表现、需要哪一种验证。验证范围按风险选择，避免写仅复述实现的测试或把简单文案变更做成大工程。

完成后留下代码、必要测试、运行命令和状态记录。若存在阻塞，说明是哪一步、错误证据是什么、已经排除什么以及下一步需要什么；不要把计划记成结果。

## 源码证据先行

1. 功能结果与用户操作以已登录 Telegram Web A 的手机尺寸界面为基线，逐项查 `TELEGRAM_WEB_PARITY.md` 的固定源码与现场证据。当前源码基线为 Web A `6002824b6532f3d913997ce496d9ab5f9b86bc22`（`12.0.48`）；线上入口、源码支持、账号权限和本工程实现分别记录。完整目标不能缩减为「核心聊天可用」。
2. 协议字段查项目固定 TDLib `1.8.69` / `4c6377aa7386c39217878a9a56d581922ad37ca4` 的 `td_api.tl`，同步核对现代 JSON C API。Web A 的行为参考不改变本项目使用 TDLib 的协议边界。`TELEGRAM_SOURCE_MAP.md` 中的 Android 固定提交可作补充研究，不能据此推断 Web A 具有对应能力。
3. 呈现与平台交互遵循 HarmonyOS 官方推荐。API 先查本机当前 SDK 26 / `26.0.0.105` 类型和已有调用，再查对应官方资料；导航、菜单、弹层、选择器、通知与权限使用官方 ArkUI / HarmonyOS 能力，不引入 Android UI 或 WebView 替代。
4. 在代码或文档里记录影响设计的来源与版本。上游升级属于独立变更，不能悄悄把 master 当固定依赖。Web A 受账号资格、群权限或浏览器能力限制的条目写清条件，不能将受限入口计为已可用。

源码来源只是行为依据，不是自动授权复制许可材料之外的资源。直接复制或翻译实现时记录来源和许可证。

## 分层验证

| 改动 | 主要证据 |
| --- | --- |
| 纯领域模型、排序、去重、草稿、恢复 | 宿主机确定性测试，覆盖正常与失败路径。 |
| 协议请求和更新归并 | 假传输注入固定 JSON，验证状态机、关联、临时 ID 替换与错误分支。 |
| ArkTS / ArkUI | 当前 SDK 实际编译，加真机交互与截图。 |
| Native 桥和第三方库 | OHOS 编译、ELF 架构及依赖检查，真机加载与无敏感数据的调用结果。 |
| 安全存储和生命周期 | 真机初始化、重启、关闭、错误恢复验证；不记录密钥值。 |
| 真实云端能力 | 用户明确授权的账号与动作，在服务端和另一客户端确认结果。 |

纯逻辑测试脚本入口为 `scripts/test-domain.sh`，其实际覆盖与执行结果见 `STATUS.md`；未运行或失败的检查不能写为「全部通过」。最终编译使用 `scripts/build.sh`，设备使用 `HDC_TARGET` 指定。

## 真机验收

使用用户明确指定的真机；`doctor.sh` 用于核对当前设备列表。真机可用时优先真机；用户已明确授权拔掉真机后使用手机模拟器继续功能测试。不得用模拟器结果补写真机或宽屏通过证据。构建、安装、启动是三步独立检查，某一步成功不能替代后续步骤。基础验收至少覆盖本次变更涉及的路径，例如列表到聊天、返回、搜索结果、输入状态和重启恢复。

截图和日志默认放在忽略目录 `artifacts/`。保存证据时说明页面、动作、预期、实际、设备型号和 API 版本；账号、手机号、验证码、私密消息和设备密钥不进入提交。需要登录时，由用户自行输入鉴权信息。功能测试遵循 `AGENTS.md` 及会话中已有授权：当前允许在自己的收藏夹使用明确合成测试内容，不向联系人代发、不上传私人相册内容；测试前保护并最终恢复原有草稿，只记录恢复比对结果，不记录正文或摘要值。

## UI 变更的附加步骤

修改界面前读 [UI 规范](UI_GUIDELINES.md)、[Web A 能力矩阵](TELEGRAM_WEB_PARITY.md) 与 [响应式验收矩阵](RESPONSIVE_VALIDATION.md)。先确认 Web A 手机尺寸下的实际功能和操作，再以鸿蒙官方组件实现；不要在实现过程中自行加入宣传文案、重复标签或开发技术说明。

以当前内容容器的可用 `vp` 宽度设计 `compact / medium / expanded`，并写出跨断点后的会话、草稿和滚动保持规则。测试矩阵包括手机、平板、大屏、折叠、阔折叠、横竖屏和分屏；设备形态是验收分类，不是代码中的型号判断。

一次 UI 交付分别记录：

1. **设计检查**：导航与文案、断点、双栏、气泡宽度、键盘与安全区规则是否在源码中落实。
2. **运行验证**：实际真机、可用窗口宽高 `vp`、方向、操作、截图与结果。
3. **未覆盖项**：缺少哪类形态真机、哪个断点或哪段状态连续性测试。未执行一律标为待验证。

当前阶段优先手机单栏的完整功能和 UI/UX，真机可用时验证用户指定的未展开形态；真机拔除时可按已有授权使用手机模拟器。当前连接目标、安装与登录结果以 `STATUS.md` 的最新记录为准。额外形态不因未来矩阵而自动进入本轮范围。折叠、展开或设备姿态变化需要用户物理操作时，保留现有结果并明确待验证动作；不能以模拟器替代指定真机形态的证据。只凭型号或截图长宽比不能断言设备当前是内屏、外屏或某种折叠状态。

## 并行协作

分配任务时写清文件所有权、接口与验证边界。例如 UI agent 修改 `pages/`，协议 agent 修改纯 `.ts` 模块，Native agent 修改 `cpp/`，集成者负责最终 HAP 构建和真机验收。

所有 agent 共享文件，不要撤销未知改动。接口变化先通知相邻模块负责人；子任务完成后报告改了什么、检查了什么、还依赖什么。不要在另一个 agent 正在构建时启动 Hvigor，也不要把部分写入的 `.so` 打入 HAP。

## 接力记录模板

在 `STATUS.md` 维护精简但可执行的记录：

```markdown
更新日期：YYYY-MM-DD
当前目标：用户需要的可观察结果
当前分支 / 工作目录：可复查的位置

本次变化：
- 行为及关键文件

已验证：
- 命令、退出结果、设备信息、证据位置

尚未验证 / 已知限制：
- 明确的能力或具体失败，不写笼统的「待优化」

下一步：
- 可直接执行的动作及前置依赖
```

只记录可重复使用的信息，不复制完整聊天过程。收到用户纠正时同步状态和相关文档；如果实际实现改变，重写旧结论，不能留下互相矛盾的「已完成」描述。

## 完成判据

一个功能完成需要实现、相关验证和已知限制说明相互一致。协议 mock 通过说明逻辑满足夹具，HAP 安装成功说明包可安装，TDLib 可加载说明 ABI 可用，只有真实账号与服务端交互证据才说明云端链路通过。Web A 全面对齐还要求能力矩阵中的适用项逐项完成验收；一批消息操作通过不能替代媒体、搜索、群管理、设置、通知、通话等其余条目的结果。
