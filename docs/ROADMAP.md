# 功能路线图

当前只推进用户阔折叠真机未展开形态的真实功能与 UI/UX。多设备、多形态验证推迟；用户已授权真机拔除后用手机模拟器继续功能测试；先解决系统栏黑边、官方玻璃导航、真实头像、消息/图片与历史草稿链路。

路线图描述推进顺序和完成条件，不表示各项已经通过。实时状态、具体产物和设备证据统一记录在 `STATUS.md`。

用户最新完整验收目标是 [Telegram Web A 手机尺寸功能对齐](TELEGRAM_WEB_PARITY.md)，采用鸿蒙官方推荐 UI/UX。下面的阶段只安排实施顺序，不缩减该范围。基线网页使用用户已登录的同一账号，包含账号配置、角色、群权限和付费能力差异；未经现场或上游源码确认的能力不擅自归为 Web 已支持。

## 阶段与验收

| 阶段 | 目标 | 完成条件 |
| --- | --- | --- |
| 原生基础 | ArkUI 会话、聊天、联系人、搜索、主题与本地持久化 | SDK 编译通过；真机可完成交互；重启保留本地内容；演示身份清晰。 |
| 协议引擎 | 固定 TDLib / OpenSSL 源码，OHOS arm64 产物与 Node-API 桥 | 构建可重现；ABI、动态依赖、符号正确；真机可创建客户端和接收认证更新。 |
| 用户登录 | 默认应用配置、手机号、验证码、二步密码、邮箱及错误状态 | 用户自行登录已有账号；Ready 来自服务端；重启恢复；不支持分支有明确提示。 |
| 文本闭环 | 云端会话、历史、文本收发、未读、置顶与静音 | 两端确认出入站消息；临时 ID 替换、失败状态、分页、重复更新与重新连接正确。 |
| 数据与生命周期 | 安全存储、加密数据库、前后台、关闭与退出 | 真机重启和失败恢复验证；账号数据隔离；停止旧客户端更新；不泄露敏感信息。 |
| 可分发版本 | 开发者自有应用 API 配置、release guard、许可和构建记录 | 正式构建不带开发用途配置；具备版本、源码和依赖清单；关键真机回归通过。 |

## 后续功能

以下能力需独立实现和验收，不能由已有文本界面推断完成：

- 图片、视频、文件、语音和贴纸的选择、上传、下载、预览、取消与失败恢复。
- 通知、通知点击跳转、后台连接与系统后台限制适配。
- 代理、连接诊断、网络切换、离线队列与重试。
- 群组和频道权限、成员管理、邀请、公开链接、转发、回复、编辑、删除与撤回。
- 服务端搜索、归档、文件夹、多账号和大历史性能。
- 通话、音视频设备与权限、隐私设置及端到端加密相关功能。
- 平板、折叠屏、自适应布局、无障碍与更多语言。

优先补足当前链路的正确性与恢复能力，再扩展媒体和复杂功能。每个功能都要对照 Telegram 实际语义列出边界，例如频道能否发言取决于权限，不能只根据 `kind === channel` 永久禁止。

## 当前集成的关键检查

1. 模式切换后旧 TDLib 更新不会污染离线演示数据，离线恢复不会被重新播种覆盖。
2. 历史分页与实时入站同时发生时不丢消息；发送回执正确替换临时 ID。
3. 会话排序保留 int64 精度，未读、置顶、静音与服务端更新一致。
4. Asset 读取失败不重新生成数据库密钥；关闭后重启可恢复同一数据库。
5. 开发者自有 API 配置通过本机文件注入；私有源文件和生成文件均未被 Git 追踪；正式 release guard 已验证拒绝缺失或无效配置。
6. 未发生账号认证和双向消息验证前，项目描述保持为「真实接入开发中」。

## 近期交付边界

当前工作以已创建的鸿蒙基础工程为起点，建立可持续迭代的原生客户端和真实 Telegram 链路。界面复刻、源码架构参考、底层协议接入和完整 Telegram 功能覆盖是不同的工作项；项目状态应逐项反映进展。
